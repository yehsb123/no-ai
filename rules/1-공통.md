# 공통 규칙

## C01 em dash

`—` 를 쓰지 않는다. 문장을 끊거나 쉼표를 쓴다.

검사: 줄 `—`

## C02 설명 안의 가운뎃점

`·` 로 설명을 잇지 않는다. 쉼표를 쓴다.

## C03 인용구 강조

`>` 인용구로 강조하지 않는다. 그냥 본문으로 쓴다.

검사: 줄 `^\s*>`

## C04 구분선

`---` 구분선으로 칸을 나누지 않는다. 제목으로 나눈다.

검사: 줄 `^\s*(-{3,}|\*{3,}|_{3,})\s*$`

## C05 굵게

`**굵게**`를 한 문단에 두 번 이상 쓰지 않는다. 다 굵으면 아무것도 안 굵다.

검사: 내장 `굵게`

## C06 기호와 이모지

기호로 경고하지 않는다. `★`, `⚠`, `①②`, `←` 대신 제목과 문장으로 쓴다. `→` 로 결론을 잇지 않고 문장으로 쓴다.

이모지도 쓰지 않는다. 보고의 ✅ 🟣 🎉, 리뷰 메시지의 🔧 💡 모두 "AI 같다", "이상한 이모지 넣지 말고"라는 지적을 받았다.

검사: 줄 `[★☆⚠❗‼←→⇒✅✔❌]|[①-⑳]|[\U0001F300-\U0001FAFF]`

## C07 말끝

한 편 안에서 말끝을 한 가지로 통일한다. 기본은 `~입니다`, `~합니다`다.

메모식 `~함`, `~임`, 반말 `~다`를 섞지 않는다. 인수인계 문서, 가이드 문서도 같다.

검사: 줄 `^(?!\s*#).*[가-힣](함|임|됨)\.?\s*$`
제외: 에세이, 메신저, 발표

## C08 번역투 단어

| 금지 | 대신 |
|---|---|
| 덩이 | 부분, 영역, 묶음 |
| 자리 (추상적으로) | 부분, 곳 |
| 쓸 일이 없습니다 | 필요 없습니다 |
| 넘어집니다 | 실패합니다 |

검사: 줄 `덩이|넘어집니다|쓸 일이 없습니다`

## C09 `것`으로 얼버무리기

제목이든 본문이든 `것`으로 얼버무리지 않는다. 무엇인지 이름을 붙인다. `건`, `걸`, `게`처럼 줄여 써도 같다 ("설치할 게 없습니다" 대신 "설치할 패키지가 없습니다").

예상을 적을 때도 `것`을 피한다. "채워질 것으로 예상합니다" 대신 "채워진다고 예상합니다".

| 금지 | 대신 |
|---|---|
| 되는 것, 안 되는 것 | 되는 기능, 빠진 기능 |
| ~하는 것 (제목에서) | 명사로 |
| 확인한 것 | 확인 결과 |
| 고친 것 둘 | 수정 두 건 |
| 배운 것 | 기록 |
| 제가 만든 것 정리 | 작업 정리 |
| 남은 것 | 남은 작업 |
| AI가 무서운 건 정상입니다 | AI가 무서워도 괜찮습니다 |

검사: 제목 `것`
검사: 줄 `것으로 예상|할 게 없`
제외: 에세이

## C10 은어와 혼자 만든 압축어

상태를 은어로 적지 않는다. "사망" 대신 "오류로 멈춤", "빈 화면"처럼 실제 상태를 쓴다. "직결확정"처럼 혼자 만든 한자 조어도 쓰지 않고 풀어 쓴다.

검사: 줄 `사망|직결확정`

## C11 억지 비유어

억지 비유어를 쓰지 않는다. 번역기로 돌린 글처럼 읽힌다.

| 금지 | 대신 |
|---|---|
| 연장은 손에 쥐어야 연장입니다 | AI는 도구입니다 |
| 연장꾼, 대장장이, 불지기 | 활용, 설계, 검증 |
| 화로 한 판 | 레슨 한 편 |

API가 아닌 개념을 리모컨에 비유하지 않는다. 리모컨이라고 하면 API로 읽힌다.

## C12 참고 작품과 다른 프로젝트 이름

참고한 작품 이름을 본문에 반복하지 않는다. 분위기는 묘사로 쓴다.

| 금지 | 대신 |
|---|---|
| 스텔라블레이드의 자이온처럼 | 협곡 속 마지막 인간 도시 |
| 자이온 비주얼 | 도시 비주얼 |

다른 프로젝트나 서비스 이름을 끌어와 설명하지 않는다. "메티베이터처럼" 대신 방식을 직접 적는다.

## C13 게임 용어

게임이 아닌 서비스에 게임 용어를 쓰지 않는다. 시민, 주민, 수첩 도장, 레벨업, 한 판 같은 말은 수강생, 학습 기록, 수료, 레슨으로 쓴다.

## C14 질문형 제목

제목을 질문으로 달지 않는다. 강의나 콘텐츠 제목도 같다. `~있나`, `~다면`, `~할까`, `~될까`로 흐리지 않고 명사로 끝낸다.

| 금지 | 대신 |
|---|---|
| 아직 안 된 것 | 준비 중인 기능 |
| 무엇을 할 수 있나 | 기능 |
| 누가 들어올 수 있나 | 접근 권한 |
| 익명이 어떻게 지켜지나 | 익명 처리 방식 |
| 만들면서 배운 것 | 개발 과정 기록 |
| 지금 없는 것 | 미구현 기능 |
| 자소서에 내 문장이 남아 있나 | 자기소개서 AI 첨삭 범위 |
| 진로를 AI에게 물었다면 | AI 진로 상담 결과 확인법 |
| AI가 계산한 세금 믿어도 될까 | AI 세금 계산 검토 |

검사: 제목 `(나|나요|까|까요|다면|는가|\?)\s*$`
제외: 에세이

## C15 경구형 제목

제목은 그 아래 내용을 가리키는 이름이다. 경구, 슬로건, 말장난, 대구로 제목을 달지 않는다. 읽는 사람이 무슨 내용인지 알 수 없고 광고 문구처럼 보여서 싫다.

    A는 B해야 A다        연장은 손에 쥐어야 연장입니다
    A가 아니라 B         남이 지켜주는 도시가 아니라 우리가 지키는 도시
    A에서 B까지          불씨에서 명장까지
    쉼표로 붙인 두 말    자이온 비주얼, 동네 형님 말투
    숫자로 끄는 말       자이온에서 가져온 네 가지 생각

| 금지 | 대신 |
|---|---|
| 연장은 손에 쥐어야 연장입니다 | 사피엔스 프로젝트 초기 브랜딩 기획안 |
| 불씨에서 명장까지 | 레벨 체계와 수료 |
| 자이온 비주얼, 동네 형님 말투 | 톤과 비주얼 |
| 자이온에서 가져온 네 가지 생각 | 자이온 설정 반영 |
| 남이 지켜주는 도시가 아니라 우리가 지키는 도시 | 시민이 지키는 도시 |

검사: 제목 `에서 .+(까지|으로|로)\s*$|아니라`
제외: 에세이

## C16 두 줄 제목 끊기

두 줄 이상 제목은 의미 단위 사이에서만 끊는다. 조사나 서술어만 한 줄에 남기지 않는다. "오픈AI 아스트라 / 개발 중단의 / 의미" 대신 "오픈AI 아스트라 / 개발 중단의 의미"로 끊는다.

## C17 읽는 사람을 약점으로 부르기

두려움이나 부족함은 사람에게 붙이지 않고 상황에 붙인다.

| 금지 | 대신 |
|---|---|
| AI가 무서운 사람을 위한 AI 강의 | AI의 발전이 두려울 때 시작하는 AI 강의 |
| AI를 못 하는 분들을 위한 | AI를 처음 배우는 분들을 위한 |

## C18 문제 제목과 버튼 이름

제목과 버튼 이름은 읽자마자 무엇인지 알 수 있어야 한다.

    문제를 말하는 제목에 주제 이름만 쓰기 ("실측 수집 속도", "데이터 정리 부담")
    눌렀을 때 무엇이 나오는지 모르는 버튼 이름 ("오류 재생")
    출처 표기를 소개 문장처럼 쓰기 ("모델 Unitree G1입니다.")

문제 제목은 무엇이 문제인지 드러나게 쓴다 ("느린 실측 수집", "경고 없는 에셋 오류"). 버튼은 보여 주는 내용의 이름으로 쓴다 ("결함 장면"). 출처는 "모델 출처: 모음 이름, 대상 이름 (라이선스)" 형식으로 짧게 적는다.

## C19 뜸들이기와 예고

설명은 결론부터 쓴다. "왜냐하면", "그래서 이렇게 됩니다" 같은 연결어로 뜸들이지 않는다. "예를 들어 보겠습니다"처럼 다음 내용을 예고하는 문장도 빼고 바로 예로 들어간다.

검사: 줄 `그래서 이렇게 됩니다|결론부터 말하면|예를 들어 ?보겠|예를 들어보자면`

## C20 자문자답

"어느 쪽을 따릅니까. 답은 더 강하게 막는 쪽입니다", "그런데 무엇을 봤습니까." 처럼 스스로 묻고 답하지 않는다. 답만 쓴다.

검사: 줄 `(니까|습니까)[.?]\s*답은`

## C21 경구로 떨어지는 문장

제목이 아닌 본문에서도 잠언처럼 딱 떨어지는 문장을 쓰지 않는다. "규정은 매번 같아야 규정입니다", "내용은 사람이, 집행은 코드가." 같은 문장은 무엇이 무엇을 하는지 풀어 쓴다. 문단 끝을 이런 문장으로 맺지 않는다.

## C22 과장

| 금지 | 대신 |
|---|---|
| 놓치기 쉬움, 오해 방지 | 빼거나 사실로 |
| 우리가 자초한 리스크 | 정정이 필요한 문구 |
| 역이용될 수 있다 | 요청을 줄이는 근거가 될 수 있습니다 |
| 가장 고약하다, 진짜 문제는 | 빼고 문제를 바로 적음 |
| 이게 핵심이다 | 빼고 내용으로 |
| 여기가 답입니다, 이게 오늘의 증거입니다 | 빼고 내용으로 |
| 실무에서 이 차이가 큽니다 | 빼거나 어떤 차이인지 적음 |

중요하다고 따로 강조하지 않는다. 중요도는 읽는 사람이 판단한다.

검사: 줄 `놓치기 쉬|오해 방지|자초한|역이용|고약|진짜 문제는|핵심이다|핵심입니다|여기가 답입니다|오늘의 증거|이 차이가 큽니다`

## C23 자기 다짐과 서문

문서에 자기가 어떤 자세로 쓰는지 적지 않는다.

    Our principles
    과장하지 않습니다
    사실만 씁니다
    정직하게 적었습니다
    투명하게 공개합니다
    특기사항 (전부 정직하게)

과장을 안 하려면 안 쓰면 된다. 안 하겠다고 적는 순간 그 문장이 과장이다.

문서 앞에 "왜 이 문서를 쓰는가" 같은 서문도 붙이지 않는다. 바로 1번으로 들어간다.

검사: 줄 `Our principles|과장하지 않|사실만 씁니다|정직하게 적었|투명하게 공개|전부 정직하게`

## C24 홍보 문구

사내 가이드나 설명 문서 본문에 회사 홍보 문구를 넣지 않는다. "그게 우리가 FDE 파견을 핵심 수단으로 두는 이유입니다" 같은 문장은 "광고용 문구 넣지 말고"라는 지적을 받았다.

## C25 추상 구호

"고객 감동" 같은 구호 대신 실제로 할 행동을 쓴다. "고객에게 문제가 생기면 바로 대응할 수 있게 미리 알고 준비합니다"처럼 쓴다.

## C26 문장 다듬기

    같은 동사를 이어지는 두 문장 끝에 반복 ("먼저 검사한 뒤 씁니다. 틀린 경우가 있어 고쳐서 씁니다.")
    "A 대신 A" 처럼 같은 말로 대구 만들기 ("데이터만 쓰는 구성 대신 섞어 쓰는 구성")
    뜻이 제자리를 도는 문장 ("버전마다 기록을 남깁니다") 대신 언제, 무엇을 남기는지 쓰기
    한 페이지 안에서 높임이 섞이기 ("원하는 형식" 과 "원하시는 형식")
    처음 보는 사람이 모를 용어를 풀이 없이 쓰기. 첫 등장에 괄호로 짧게 푼다 ("물성값(질량, 마찰)")
    영어 약어를 어색한 한국어로 옮기기 ("HITL은 휴먼루프" 대신 "사람이 중간에 확인하는 단계(HITL)")

## C27 요청하지 않은 해명과 면책

요청하지 않은 해명, 면책, 안내 문구를 산출물에 넣지 않는다. 로고 줄 아래 "로고는 각 회사의 상표이며, 작업과 납품에 쓰는 도구를 나타냅니다"를 넣었다가 강하게 질책받았다. 상표나 법적 우려는 채팅으로 한 줄 말하고, 넣어야 한다고 보면 먼저 묻는다.

작업 메모도 산출물에 넣지 않는다. "지금은 넣지 않았습니다", "~로 잡았습니다", "~를 표시했습니다"처럼 무엇을 빼고 가정했는지 설명하는 문장은 채팅으로 말한다. 기획안의 결정 목록에는 정할 항목과 선택지만 적는다.

## C28 겉치레

내용보다 꾸밈이 많으면 AI 가 쓴 티가 난다.

    두세 줄짜리를 표로 만들기
    문단마다 굵게
    빈 확인 칸이 있는 표 ("| 확인 | 항목 |"), 준비물 표
    짧은 글에 "## 결과", "## 정리" 같은 제목 붙이기
    번호와 기호로 층 쌓기

줄글 서너 줄이면 되는 내용을 표로 만들지 않는다. 표는 항목이 여럿이고 칸이 맞아떨어질 때만 쓴다. 만들 항목은 목록으로 보여 준다.

검사: 제목 `^#+\s*(결과|정리|요약|결론)\s*$`

## C29 문단 길이

문단은 두세 문장까지. 길어지면 자른다.

검사: 내장 `문단길이`

## C30 반복과 군더더기

같은 설명을 여러 곳에 되풀이하면 글이 길어지고 읽는 사람이 핵심을 놓친다. 가장 많이 지적받은 문제다.

    한 페이지에 같은 조건 문구 반복 ("지정하신 시뮬레이터 버전에서 불러오기, 충돌, 관절 범위 검사" 여섯 번)
    옆에 목록이 있는데 본문에서 목록을 다시 문장으로 풀기
    제목이 이미 말한 내용을 첫 문장에서 한 번 더 말하기
    목록 항목 끝마다 "~하는 작업" 붙이기
    요약 장과 부록에서 본문을 다시 말하기, 요약과 상세를 함께 넣기

조건과 범위는 한 곳에만 자세히 적고, 나머지는 짧게 가리킨다. 문장 하나를 빼도 뜻이 같으면 뺀다. 요약 장이나 부록이라는 역할을 이유로 반복을 남기지 않는다.

## C31 위치와 화면

기능 설명에는 위치를 넣는다. "좌측 하단의 FSW 가이드라인에서 볼 수 있습니다"처럼.

화면을 붙일 수 있으면 레이아웃을 문장으로 묘사하지 않는다. 이미지는 설명 바로 뒤에 놓고, 필요하면 이미지 뒤에 한 줄 더 붙인다. 캡처 아래에는 화면에 안 보이는 규칙(권한, 기본값, 실패 조건)만 남긴다.

## C32 확인한 범위

확인한 만큼만 쓴다. 넓게 쓰면 한 번 틀린 문장 때문에 글 전체를 믿지 않게 된다.

    "파일만 있으면 됩니다" 처럼 할 수 없는 일까지 덮는 말
    측정은 한 곳에서 했는데 "대부분", "많습니다" 로 넓히기
    제목은 "10종 이상" 인데 나열은 9개
    출처 주체를 뭉뚱그리기 (다른 단체가 만든 모델을 "제조사 모델" 로)
    다른 회사 이름을 제휴나 보증처럼 읽히게 쓰기

할 수 있는 부분과 대조가 필요한 부분이 섞이면 둘로 나눠 적는다. 숫자와 개수는 같은 페이지의 다른 곳과 맞춘다. 판단이 필요하면 근거를 함께 적는다.

## C33 이유는 직접 원인으로

"왜"를 적는 곳에는 직접 원인을 쓰고, 그 결과는 따로 적는다. "2주가 날아갑니다"를 이유로 쓰지 않고 "폐쇄망 계정은 신청해야 나옵니다. FDE가 접수해야 발급이 시작되고 2주에서 4주 걸립니다"로 쓴다.

## C34 숫자

숫자는 한 번 틀리면 나머지 숫자까지 의심받는다.

    무엇의 개수인지 빼기 ("테스트 59개" 는 파일 59개인데 케이스 수로 읽힌다)
    세는 기준 빼기 (같은 코드가 주석 포함 여부에 따라 531, 612, 753줄)
    어느 시스템, 어느 시점 값인지 빼기 ("자유게시판 222건" 은 옛 시스템 값, 지금은 28건)
    모르는 값을 0으로 쓰기 ("언급량 0회", "-100%" 대신 "데이터 없음")
    "수천", "대량" 같은 규모 표현을 근거 없이 쓰기
    한 표에 통화 섞기 ($1,999 와 1,240만원)
    검색가, 견적가, 확정가를 같은 형식으로 쓰기
    올해가 아닌 날짜에 연도 빼기 ("11.1 ~ 12.31" 은 올해 행사로 읽힌다)

숫자에는 단위, 세는 기준, 잰 날짜를 붙인다. 진행 중인 과제의 숫자는 "9월 28일 기준 99건"처럼 시점을 적는다.

통화는 원화로 맞추고 원문 통화를 괄호에 둔다. 환율과 기준일은 한 번 적는다.

AI 모델 이름, 가격, 순위처럼 몇 달 안에 바뀌는 정보에는 "2026년 9월 기준"처럼 기준일을 붙인다.

## C35 여러 곳에 적힌 숫자

같은 숫자가 여러 문서에 있으면 고칠 때 그 숫자를 적은 곳을 모두 찾는다. 측정이나 자동 계산으로 바뀌는 값은 정본 한 곳에만 적고 나머지는 가리킨다.

숫자를 고쳤으면 이전 값, 새 값, 날짜를 함께 남긴다. "처음 적은 3,962줄은 잘못 센 값입니다. 9월 28일에 다시 세어 4,062줄로 고쳤습니다."

## C36 검증과 판정

"테스트 완료", "정상 동작 확인", "100%", "완벽"은 읽는 사람이 다시 확인해야 하는 말이다.

    검증한 범위를 적지 않고 "오류 없음", "완벽합니다"
    대상이 0건인 검사를 "통과" 로 적기
    목록을 끝까지 보지 않고 "없습니다" 로 판정하기
    직접 확인한 숫자와 기록에서 옮긴 숫자를 섞기
    실행 전 예상을 사실처럼 단정하기
    "임의로", "알아서", "자동으로" 로 동작 규칙을 흐리기

무엇을 몇 건에 대해 어떻게 쟀는지 적는다. "17개 시스템, 화면 이동과 뒤로 가기 정상, 원문 22,295자 왕복 일치, JS 오류 0건." 안 해 본 경로는 안 해 봤다고 적는다.

대상이 0건이면 "잰 대상 없음"으로 적는다. 목록을 다 보지 않았으면 "확인한 범위에서는"을 붙인다.

측정값에는 도구, 버전, 날짜를 붙인다 ("MuJoCo 3.12, 2026-09-28"). 판정은 정상, 이상, 검증불가처럼 정해 둔 값으로만 쓰고, 검증불가는 무엇이 있어야 가능한지 함께 적는다. 동작은 실제 규칙으로 쓴다 ("형상 부피에 물 밀도 1000 kg/m³를 곱해 질량을 계산합니다").

확인하지 못한 출처는 본문 사실로 쓰지 않고 "국내 기사로는 확인하지 못했습니다"처럼 따로 적는다. 발표된 원인과 해석을 섞지 않는다.

검사: 줄 `완벽합니다|완벽하게 (동작|작동)|100% (정상|완료|일치)`

## C37 같은 이름 쓰기

    한 문서 안에서 같은 대상을 두 이름으로 부르기 ("운영 계층" 과 "오케스트레이션 계층")
    제품명 표기 섞기 (SO-101, SO-ARM101, SO101)
    이미 이름이 있는 대상에 혼자 줄임말 붙이기 ("피어가 재현했습니다" 대신 "EZwork 세션이 재현했습니다")
    화면 라벨 대신 코드 상수 쓰기 (USER, ADMIN 대신 일반 사용자, 관리자)
    바뀐 기능을 옛 이름으로 부르기 (레벨을 정하지 않는 진단을 "레벨 진단" 으로)
    사용자가 정한 틀과 이름을 바꿔 부르기 ("명심할 3가지"를 "세 단계 구조"로, "재설계"를 "이관"으로)

첫 등장에 정식 이름을 쓰고 이후 줄임말을 고정한다. 기능이 바뀌면 이름, 버튼, 메뉴, 안내 문구를 같이 바꾼다.

기능 위치를 옮기면 옛 위치를 가리키는 안내 문구와 문서를 찾아 함께 고친다. 정해지지 않은 이름에는 "(가칭)"을 붙인다.

## C38 절 번호로 가리키기

문서의 절 번호로 다른 곳을 가리키지 않는다. 번호는 다른 작업이 먼저 쓰면 밀린다. 가리켜야 하면 절 제목을 함께 쓴다 ("PRD 122" 대신 "PRD 124 (커뮤니티를 우리 표로 되돌린다)").

## C39 동료 이름과 평가

노트와 칸반은 모두가 본다. 동료 이름을 걸어 의견을 인용하지 않는다.

배경은 남긴다. 누가 말했는지 대신 어떤 의견이 있었는지를 쓴다. 왜 이 작업이 생겼는지가 보이면 충분하다.

동료의 말을 평가하지 않는다. 맞다, 근거 있다, 실질은 이것이다 같은 판정을 붙이지 않고, 확인한 사실만 이어서 쓴다.

| 금지 | 대신 |
|---|---|
| 개발자(홍길동) 제기: "여유있게 받아야 할 거 같습니다" | 크롤러 부하 때문에 여유 있는 사양이 필요하다는 의견이 있었습니다 |
| 근거 있는 우려다 | 빼고 확인 결과를 바로 적음 |
| 홍길동 우려의 실질이 여기다 | 증설에 시간이 오래 걸리면 처음부터 여유 있게 받아야 합니다 |

담당자는 카드의 담당자 칸과 멘션으로 표시한다. 본문에는 이름을 쓰지 않는다.

외부 담당자 연락처처럼 이름 자체가 정보인 경우만 예외다. 문서 머리말의 담당자 줄도 본문으로 보고 이름을 빼며, 기획안 화면에도 동료 이름을 넣지 않는다.

동료가 쓴 문서는 규칙에 어긋나도 직접 고치지 않고 어긋난 부분만 사용자에게 알린다.

검사: 줄 `(개발자|담당자|PM|책임|선임|매니저)\s*\([가-힣]{2,4}\)|근거 있는 우려|우려의 실질`

## C40 사람이 고친 문장과 줄이기 요청

사용자나 검토자가 직접 고친 문장은 기준으로 삼고 건드리지 않는다. 나머지 문장의 말투를 그 문장에 맞춘다.

줄여 달라고 하면 분량을 실제로 줄인다. 단어 몇 개만 바꾸고 문장 구조를 그대로 두면 "줄어든 건 없는 거야?"라는 말을 듣는다. 사람이 쓴 글을 다듬을 때는 문장 구조를 살리고 필요한 부분만 바꾼다.

## C41 외부 공개 글의 이름

외부에 공개하는 글과 범용 도구에서는 고객사명, 제품명, 동료 이름, 만든 계기가 된 프로젝트 이름을 빼고 "사내 해운 시황 대시보드"처럼 일반 명사로 쓴다. 외부 자문을 옮길 때도 이름 대신 역할로 쓴다 ("현업 로봇 연구원 의견으로는").

## C42 파일마다 담는 내용

한 파일에 다 넣지 않는다. 읽는 사람이 다르면 파일도 나눈다.

| 파일 | 읽는 사람 | 담는 내용 | 담지 않는 내용 |
|---|---|---|---|
| EZ Work 노트 | 팀 전체 | 화면과 기능, 쓰는 방법, 캡처 | 코드, 파일 경로, 커밋 해시 |
| 칸반 티켓 | 담당자와 관련자 | 배경, 조사 결과, 결정 사항, 남은 결정 | 동료 이름, 동료 의견에 대한 평가 |
| 인수인계 `README.md` | 다음 담당자 | 구조, 설계 이유, 밟은 함정, 남은 작업 | 사용법 |
| `docs/PRD.md` | 개발자 | 제품 정의, 범위, 아키텍처 결정 | 진행 상황 |
| `docs/PROGRESS.md` | 개발자 | 마일스톤 체크, 현재 상태 | 왜 그렇게 정했는지 |
| `docs/USER_GUIDE.md` | 앱 사용자 | 화면과 버튼 기준 사용법 | 개발 상태, 미구현 표시 |
| 커밋 메시지 | 나중의 나 | 왜 고쳤는지, 무엇이 깨졌었는지 | 무엇을 했는지만 나열 |
| 코드 주석 | 그 코드를 고칠 사람 | 왜 이렇게 했는지 | 코드를 읽으면 아는 내용 |
| 검사 스크립트 | 돌리는 사람 | 무엇을 재는지, 왜 그걸 재는지 | 결과 요약 |

같은 내용을 두 파일에 적지 않는다. 한쪽을 고치면 다른 쪽이 낡는다.

## C43 진행 보고의 사고

진행 보고에서 내가 낸 사고는 결과 앞이나 바로 뒤에 한 줄로 적고, 복구 방법을 같은 줄에 붙인다. 사과나 반성은 적지 않는다.

## C44 빈 수식어

뜻을 더하지 않는 수식어로 문장을 채우지 않는다. 무엇이 어떻게 좋은지를 쓴다.

| 금지 | 대신 |
|---|---|
| 혁신적인 기능, 획기적인 개선 | 어떤 일이 몇 분에서 몇 초로 줄었는지 |
| 다양한 기능을 제공합니다 | 기능 이름을 적음 |
| 효율적이고 체계적인 관리 | 무엇을 어떻게 관리하는지 |
| 원활한 소통을 위해 | 빼거나 목적을 바로 적음 |
| 게임 체인저, 새로운 지평 | 빼고 결과를 적음 |

검사: 줄 `혁신적|획기적|게임 ?체인저|새로운 지평|패러다임 전환`

## C45 여러 번 고친 뒤 전체 다시 읽기

한 부분씩 여러 번 고친 글은 마지막에 처음부터 끝까지 다시 읽는다. 부분만 고치다 보면 전체 흐름이 어긋난다.

    본문에는 정했다고 적고 결정 목록에는 아직 안 정했다고 적기
    확정된 내용을 결정 목록에 남기기
    뒤에서 설명할 용어가 앞에 먼저 나오기

다시 읽을 때는 반복(C30)과 이름(C37)도 한 섹션이 아니라 문서 전체를 기준으로 본다.

고친 결과를 보고할 때는 무엇을 기준으로 전체를 다시 읽었는지 함께 적는다.
